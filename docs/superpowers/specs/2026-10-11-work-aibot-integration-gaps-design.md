# 智能机器人接入能力补齐设计

状态：2026-10-11 已按用户授权完成方案审查及实施；独立实现审查发现已修复，全仓、Go 1.23、race 和静态检查通过。用户后续已授权再次审查通过后提交，实施、复核及验证记录见对应计划。

## 目标与范围

根据使用项目 `wecombot` 的六项反馈，补齐 SDK 的公共模型、素材校验、文件名来源、首次连接恢复、回复期限及限流接入点，让项目可以删除重复的协议实现。保持 Go 1.23、现有三个接入子包、日志脱敏、原始 context、错误链、连接代际隔离和不自动重放业务请求的约束。

本轮修改 `wx` SDK。使用项目仅作为需求和迁移验证依据，不在本轮修改其源码或依赖。分布式租约、消息去重、领域转换、回复引用映射及淘汰、工作队列、背压、卡片内容、附件降级与补偿由项目负责。

`v2.5.0` 已创建，因此采用新增字段、方法和配置项的方案，不删除或改名现有 API。公共结构体新增字段会影响使用未命名字段初始化的消费者，应在迁移说明中提示使用命名字段。

## 核对结论和官方依据

已读取 SDK 及反馈指向的项目代码，并于 2026-10-11 重新获取官方长连接文档。Web 浏览工具无法打开该页面，使用 HTTP 下载的官方页面核对正文；快照位于 `/tmp/wx-aibot-gap-reference/doc-101463.html` 和 `.txt`，不作为仓库依赖。

官方依据：

- [智能机器人长连接协议](https://developer.work.weixin.qq.com/document/path/101463)：普通回复 24 小时；欢迎语及卡片更新 5 秒；流从首次发送起 10 分钟；每会话回复及主动发送合计 30 条/分钟、1000 条/小时；每机器人上传 30 次/分钟、1000 次/小时；素材大小、格式、分片约束。
- [官方 Node.js SDK API 文档](https://github.com/WecomTeam/aibot-node-sdk#-api-文档)：欢迎语和卡片更新的 5 秒要求，以及连接、素材和下载接口的使用方式。

核对结果：

| 反馈 | 现状和处理 |
| --- | --- |
| 回调模型重复 | SDK 已覆盖消息、事件、引用和混合消息；增加可选 `filename` 扩展，项目改为 SDK 模型到领域消息的转换 |
| 素材预检重复 | 上传大小和最少 5 字节已校验；缺少公共限额查询及高层上传的格式校验 |
| 下载文件名来源缺失 | `Filename` 混合了响应头、URL 和默认回退名称；增加明确的响应头文件名 |
| 首次连接不重试 | 当前仅首次订阅成功后启动重连；增加显式首次连接重试策略和错误分类 |
| 回复期限未校验 | 目前只有来源、连接代际和请求超时校验；普通回复、欢迎语、卡片和流均需补协议期限 |
| 上传限流口径 | 项目按连接统计上传，会在重建客户端后重置；发送和上传是两套独立额度，不能合并 |

普通消息和引用中的 `filename` 未见于当前官方必填字段表，作为可选扩展保留；不能把它变成回调合法性的前提。官方文档未明确流式每次刷新及卡片更新如何扣减发送次数，本轮不把猜测写成默认计数算法。

## 方案选择

推荐在现有包内增补公共能力，新增配置显式启用首次连接重试和限流。这样项目可以逐项迁移，已有调用者的首次连接等待行为及限流行为保持兼容。

另外两种方案不采用：只导出工具函数无法覆盖排队后的期限检查及上传入口的一致性；再次整体重构会扩大已发布版本的迁移成本，而且不解决平台计数口径未明确的问题。

## 1. 公共回调与下载模型

- `aibot.DownloadContent` 新增 `Filename string`，JSON 标签为 `filename,omitempty`，普通文件、视频、图片及引用复用该模型。`Callback.Raw` 和 `Frame.Raw` 继续完整保留未知字段。
- `aibot.DownloadedMedia` 新增 `HeaderFilename string`，仅表示实际下载响应 `Content-Disposition` 中解析成功并安全清洗后的名称；无有效响应头名称时为空。
- 现有 `Filename` 的选择顺序和含义不变：有效响应头名称、URL 路径名称、`media`。不为这两个字段引入回调文件名的隐式覆盖逻辑。
- 延续 `filename*`、跨平台路径分隔符、控制字符、空名的处理。响应头来自最终下载响应；下载、原始下载、Webhook 默认密钥下载和长连接下载统一走公共实现。
- 项目可采用 `HeaderFilename → callback.Filename → Filename` 的业务优先级，并删除 `mediaResponseTransport`。

## 2. 公共素材限额与预检

在 `aibot` 根包提供：

```go
type MediaLimits struct {
    MinBytes int64
    MaxBytes int64
    Formats  []string
}

func UploadMediaLimits(mediaType string) (MediaLimits, error)
func ValidateUploadMedia(mediaType, filename string, data []byte) error
```

- 限额统一为至少 5 字节；image/video 10 MiB、voice 2 MiB、file 20 MiB；文件名非空、有效 UTF-8、不超过 256 字节。返回的格式列表不暴露可修改的全局状态。
- 图片支持 PNG/JPEG/GIF，语音支持 AMR，视频支持 MP4，普通文件不限制格式。依据内容签名及必要的容器头检查，不只根据后缀或 HTTP Content-Type 判断。MP4 检查不能把带 `ftyp` 的任意其他格式直接当作 MP4，也不宣称已验证所有视频编码和完整解码。
- `UploadMedia` 在完成有界读取后、任何初始化请求前调用同一预检。读取上限同时取平台上限、配置上限和最多 100 片的容量。
- `InitUpload` 复用可依据元数据检查的大小、文件名和分片规则；它没有文件内容，不能承诺格式校验。低层三步骤接口继续允许调用方管理上传状态。
- 流式内嵌图片和卡片图片使用原有 JPG/PNG 规则；上传支持 GIF 不改变这些独立规则。
- 错误继续支持 `errors.Is(err, ErrInvalidArgument)`，具体失败原因由错误信息说明。此校验是本地预检，最终内容合法性仍由平台检查。

## 3. 首次连接重试及错误分类

- `websocket.Config` 新增 `InitialConnect *ReconnectPolicy`。nil 保持当前首次连接仅尝试一次；显式配置支持 0 次重试、有限次数或 -1 无限重试。计数为首次尝试之外的重试次数。
- `Reconnect` 保持管理首次就绪后的重连。两个阶段使用各自的退避、次数和上限；第一次就绪后不再使用 InitialConnect。重连后仍必须重新订阅。
- 新增类型化连接错误，提供失败阶段（拨号/订阅）、是否暂时性失败和原始错误链；外层仍使用 `core/errors.Error`，保留 HTTP 状态、errcode、req_id。重试耗尽提供可识别错误，不丢最后一次原因。
- InitialConnect 默认只重试可识别的暂时性网络故障、单次拨号/订阅超时，以及 HTTP 408、429、5xx。HTTP 401/403/404、证书校验失败、协议错误、无效配置及未知自定义错误终止。跨 errors.Join 分支的永久原因优先，显式 HTTP 状态先于泛化网络分类，ErrDisconnected 本身不是暂时性证明。首次就绪后的 Reconnect 维持原行为。订阅非零 ACK 保守终止，保留原码，不猜测哪些认证拒绝可恢复。
- 整个生命周期 context 取消、Close、通知溢出和被其他连接替换始终终止；单次操作的 deadline 与生命周期取消须区分。
- Connect 仍等待首次成功订阅或终止，New 不联网。初始重试期间业务继续消费状态/错误通知。定时器、拨号和订阅均可取消，失败连接在重试前关闭。
- 项目启用 InitialConnect 后删除重新创建客户端的外层无限重试；只有凭据/配置更换或业务明确重新启动才创建新的生命周期。不自动重放任何发送或回复请求。

## 4. 接收时间、回复期限与流状态

- `websocket.ReceivedCallback` 私有保存读循环收到完整帧时的本地时间，在任何待就绪队列和通知队列之前记录，公开只读方法 `ReceivedAt() time.Time` 和 `ReplyDeadline() time.Time`。公开 Callback/Frame 被修改不能改变时间、目标和期限。
- 普通消息 ReplyDeadline 为 ReceivedAt + 24 小时；enter_chat 和 template_card_event 为 +5 秒；不可回复的其他事件返回零时间并继续由 Reply 返回 ErrUnsupported。
- Reply 在入口、同回复串行队列之后、限流之后及实际取得写锁时检查期限。未写出的超期操作返回可由 errors.Is 识别的 `ErrReplyExpired`，不发送帧、不破坏当前正常连接。
- 协议限制的是发送期限。排队及实际写入受该期限约束，已经按时完成写入的请求继续使用原请求预算等待 ACK；不能把 5 秒机械用作整个 Write+ACK 的新超时。写入途中取消或发送后交付不明继续沿用原关闭规则。
- 流在同流串行锁内按 stream.id 维护第一次发送时间和已 finish 状态。10 分钟从首次取得写锁后开始写入计算，不从用户发消息或首次 ACK 算起；限流拒绝及未写出过期不能启动流，finish 仅在成功 ACK 后生效，平台明确拒绝允许修正。后续不能刷新已结束或超时的流，结束一个 ID 不妨碍同回调启动其他 ID。流更新还受原回调回复期限约束。
- 可值复制的 ReceivedCallback 通过私有共享状态指针保存流状态，不能因复制目标重置计时或复活流。
- 流状态归属于 SDK 创建的回复目标及连接代际，连接终止后不得用于新连接；不要为每条消息创建全局无界定时器或长期历史缓存。已结束状态在目标存活期间保留，避免同一目标复活结束的流。
- 本地接收时间无法消除网络传输延迟，平台仍有最终期限判断权。本轮不把 WebSocket 的 24 小时/10 分钟规则套用到 Webhook 或 response_url。

## 5. 限额说明与可注入限流

- 导出两套命名明确的官方限额：会话发送 30/分钟、1000/小时；机器人素材上传 30/分钟、1000/小时。补全 README，明确当前未默认实施本地限流。
- `websocket.Config` 新增可选 `Limiter`，接口采用 `Allow(context.Context, LimitRequest) error`；nil 保持现有行为。SDK 不增加默认滚动窗口算法、分布式存储或业务重试队列。
- LimitRequest 包含操作、维度、BotID、会话 ID、会话类型、req_id、stream.id 及首次/刷新标志。不得包含 Secret、AESKey、下载/回调 URL 或消息正文。
- 普通回复、流首次/刷新、欢迎语、卡片更新和主动发送均走发送接入点；SDK 提供操作类别，适配器可依据核准规则决定是否扣额度。单聊会话 ID 取原始回调的 From.UserID，群聊取 ChatID；Send 使用调用方 chatID。路由元数据使用私有快照，不能被消费者修改公开回调绕过。
- 一次上传在 InitUpload 接入机器人上传额度；UploadMedia 通过 InitUpload 统一接入，不能重复扣额度。Chunk 和 Finish 不作为独立文件上传再扣额度。按初始化尝试进行准入是 SDK 接入设计，并非声称官方已说明失败上传如何计数。
- 重连不更换注入的 limiter；多个客户端/副本可共享同一实例，项目负责跨副本原子计数。SDK 只调用注入点，不承担全局租约。
- 顺序为流串行锁、req_id 串行锁、状态/期限检查、limiter、再次检查、写锁、最后检查/记录流起始、Write、ACK。限流在业务调用路径执行，不能占据连接写锁或阻塞读循环、订阅和心跳；注入实现必须遵守原 context、请求预算、回复期限与连接取消，不用额外不可取消 goroutine 包裹。拒绝后原错误链保留，返回前尚未写出的操作不关闭连接。
- 没有可确定的会话标识时不得把全部消息静默计入空会话额度；使用 limiter 的操作返回明确参数错误。未注入 limiter 时维持原校验行为。

## 6. 验证与项目迁移

回归覆盖：

- filename 在普通/引用/混合模型中保留，未知字段与 Raw 不丢失。
- HeaderFilename 的 header、filename*、URL 回退、默认回退、非法名称，以及三种下载入口一致性。
- 各素材大小上下界、真实最小格式样本、错后缀、截断/错误签名、GIF 上传允许但流式图片拒绝、错误预检无网络请求。
- 首次网络失败恢复、订阅超时恢复、拒绝立即终止、有限/无限重试、取消退避、Close、HTTP 分类、通知顺序、无业务消息重放。
- 普通消息/欢迎/卡片期限、通知滞留、同 req_id 队列等待、限流等待、写锁等待、按时写出后延迟 ACK、公开模型修改不能延长期限、旧连接失效。
- 流首次计时、十分钟边界、finish 后拒绝、并发 finish/refresh、排队后期限检查及取消释放。
- 发送与上传两维度、所有发送入口、上传不重复扣额度、单聊/群聊标识、共享 limiter 跨重连、拒绝不写入、context 值/取消和敏感信息不进入日志。
- Go 1.23 全仓测试、相关 race、vet、shadow、golangci-lint、goimports 和 diff 检查。

实现后给出迁移示例：复用 aibot.Callback/Message/Event 模型；删除自写媒体格式规则和响应头 Transport；启用 InitialConnect 并尊重 SDK 终止结果；引用淘汰使用 ReplyDeadline，但容量管理继续留在项目；上传和发送分别接入共享限流器。实际平台联调只覆盖具备凭据、指定会话和授权条件的能力，不把缺条件的检查记为通过。
